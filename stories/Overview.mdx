どのカテゴリに置くか迷ったときの判断基準をここにまとめます。

## 何を置くか / 置かないか

### Foundations

個別の部品ではなく、カタログ全体が乗っている**土台**。トークン・色・タイポグラフィ・
アイコンセットなど、単体の UI パーツとして使うものではなく「他の全部品が参照する値/素材」を置く。

### Layout vs Surfaces

どちらも「骨格プリミティブ」だが、**地の色を持つかどうか**で分ける。

- **Layout**: 余白と配置だけを扱う。背景色・境界線・影を持たない（Stack / Grid / Spacer など）。
- **Surfaces**: 面。背景・境界・影を持ち、その上に他の要素が乗る（Surface / Paper / Panel / Card）。

判断に迷ったら「これを透明にしても成立するか」で聞く。成立するなら Layout、成立しないなら Surfaces。

### Page vs Layout

**Page** はアプリの骨格として**画面上の位置が決まっている**もの（AppBar は上、Footer は下、
PageLayout は画面全体の器）。**Layout** はどこにでも置ける汎用の配置プリミティブ。
「この部品はアプリ内で1箇所にしか出てこない」と言えるなら Page。

### Actions vs Inputs

**Actions** は押すと何かが起きる（ナビゲーション/コマンドの実行）。**Inputs** は値を編集して
呼び出し元に返す。フォームの一部として値を持ち回るなら Inputs、押した瞬間に完結するなら Actions。

見た目がボタンでも、押した結果が「値の変化」なら Inputs。Controls（Checkbox / Radio / Toggle）と
Stepper は押す操作だが `value` / `onChange` を持つ値エディタなので Inputs に置いている。

### Data Display vs Feedback

**Data Display** はある時点の状態を表す**静的な表示**（Badge / Chip / Status など、再描画されるまで
変わらない）。**Feedback** は処理中や処理結果を**一時的に**伝える（Toast は数秒で消える、
Spinner は処理が終わると消える）。「消えることが前提か」で聞き分けられる。

### ラベル系6部品の使い分け

「小さいラベル」を出す部品が Data Display に 6 つある（Badge / Chip / Lozenge / StatusBadge /
StatusDot / CountChip）。どれを使うかは、上から順に答えて最初に当たったものを選ぶ。

1. **押せる・消せるか？** → **Chip**（唯一 `button` 要素）
2. **中身が数値だけか？** → **CountChip**
3. **ラベル文字を置く場所がないか？** → **StatusDot**
4. **実時間で変化し続ける状態か？** → **StatusBadge**
5. **オブジェクトの工程・区分か？** → **Lozenge**
6. **それ以外のメタ情報** → **Badge**

決め手は **StatusBadge だけが `pulse` を持つ**こと。明滅は「今この瞬間の状態」を表す装置なので、
実時間で変わるものだけが StatusBadge という線引きは実装とも合う。Badge が唯一 `neutral` / `pro` と
角丸矩形を持つのは、セマンティック色に乗らないメタ情報を扱う部品だから。

この 3 分割（数値 / 状態 / 分類・対話）は Atlassian（Badge / Lozenge / Tag）と
Primer（CounterLabel / Label / Token）が独立に到達した同じ軸。**ただし名前は業界と逆**で、
Atlassian の `Badge` は数値を指すがこの DS の `Badge` は状態、数値は `CountChip` にあたる。

#### やってはいけないこと

- **Chip を非対話のラベルに使わない。** `button` 要素なので、押せないのに Tab でフォーカスが
  止まり、`aria-pressed` が意味のない値を報告する。見た目が近くても Badge / Lozenge を使う。
- **Badge で赤を出そうとしない。** Badge に赤は無く、`tone="accent"`（旧名 `danger`）が出すのは
  ブランドのコーラル。真の赤が要る状態表現は StatusBadge か Lozenge の `danger`。
- **同じ画面で Lozenge と StatusBadge を混在させない。** どちらも大文字ピルで、差はウェイト
  （600 / 800）と 1px の枠だけ。並ぶと 2 種類あること自体が読み取れない。
- **Lozenge の `tone="accent"` を Chip の近くに置かない。** 塗りと文字色が Chip の selected と
  同一で、押せるものと押せないものが同じ色になる。
- **1 つの対象に状態ラベルを 2 つ以上付けない。** 状態ラベルは目立つことで機能するので、
  並べるほど 1 つあたりの効果が下がる。
- **StatusDot 単独で状態を伝えるときは `label` を省略しない。** 省略すると `aria-hidden` になり
  支援技術から消える。色だけが情報を担っている状態は、色覚特性によっては伝わらない。

#### トーンの語彙

状態を色で表す部品は `SemanticTone`（`success` / `warning` / `danger` / `info` / `neutral`）を
共有する。Badge と Lozenge はこれにブランド強調の `accent` を足し、Badge はさらに `pro` を持つ。
Badge の旧名（`live` / `warn` / `danger`）は別名として受けるが、新しいコードでは使わないこと。

### Overlays

ページの上に重ねて出す層。Modal / Popover / BottomSheet など、元のレイアウトを覆う/浮かせるもの。

### Navigation

同一ページ内でコンテンツの表示範囲を切り替えるもの（Tabs / Accordion）や、複数ステップの
進行を示すもの（StepFlow）。値そのものを編集する Stepper（数値増減）は名前が似ているが Inputs。

### Patterns

**複数のプリミティブを組み合わせた具体ユースケース**。単体の部品ではなく「この画面ではこう組む」
という一例を見せるためのもの。**汎用性より用途が先に立つ**なら Patterns（例: FeedItem は
Avatar + UserLabel + 本文 + アクションの組み合わせ）。単体で再利用できる部品は他のカテゴリへ。

## 新しい部品を足すとき

1. 上の表の判断基準に沿って、まず「地の色を持つか」「押すのか編集するのか」「一時的に消えるか」
   のような**二択の質問**でカテゴリを絞る。
2. 既存の同カテゴリの部品と役割が似ているか見比べる（迷ったら近い部品と同じカテゴリに置く）。
3. `meta.title` は `<カテゴリ>/<部品名>`（例: `Inputs/Input`）。カテゴリ名は上の一覧の表記
   （複数形・スペースを含む表記も含め）とそろえる — 表記ゆれがあるとサイドバーでカテゴリが分裂する。
4. どのカテゴリにも当てはまらない場合だけ、このページに新しいカテゴリを足すことを検討する
   （`.storybook/preview.tsx` の `storySort.order` にも追加すること）。
